# 交接：确认自更新、主页更新按钮、每次改动一条命令发布、发布 0.2.0

- 日期：2026-10-28（KST）
- 用户的问题：项目有没有向客户端自动推送新版本的功能？0.1.0 里没看到"检查更新"按钮；如果有，每次修改都发布新版本
- 提交：`c8079af`（主页按钮 + `ship.sh`）、`588dea1`（`ship.sh` 修正 + 文档）、`2c34315`（`Release 0.2.0`，由脚本生成），以及本次收尾的文档提交
- 发布：go-nx `win-x64` **0.2.0（versionCode 200）**，18.4 MiB，sha256 `0430eabb990784c20fa7f0c1b516a0f952439d9c73e6fc17d68b1111ad021c4f`。线上现在是 0.1.0 + 0.2.0，0.2.0 是 stable 最新

## 1. 回答：有没有？

**有**，从 0.1.0 起就有应用内自更新（经本机 release-publish，Ed25519 签名 + SHA-256 校验）：启动 30 秒后检查一次，之后每 6 小时一次，下载到 `go-nx.exe.new`，**只有用户点击之后**才替换并重启（重启会断开远控会话，所以不自动）。

**你没看到按钮的原因**：0.1.0 里入口只有**系统托盘右键菜单**（顶部灰色的 `go-nx v0.1.0`，下面是更新项）；窗口里没有。Windows 11 常把托盘图标收在右下角 `^` 溢出区里。上一份交接文档把"主页也显示更新提示"列为了可选项，没做。若你装的是自己 `go build` 的 exe（版本号是 `dev`）或用了 `-no-update`，则托盘也没有更新项。

## 2. 做了什么

| 项 | 内容 | 位置 |
|---|---|---|
| 主页更新入口 | 标题旁显示版本号；右上角按钮文字随状态变化：`Check for updates` → `Checking for updates...` → `Downloading vX (n%)...` → `Up to date - check again` / `Update check failed - retry` / `Restart to update to vX`。有待安装的更新时按钮高亮，第一次点变成 `Click again to restart now`，第二次才安装并重启。检查失败的原因显示在消息行。dev 构建 / `-no-update` 没有按钮，点原位置会提示原因 | `internal/ui/home.go`、`cmd/go-nx/{main,update}_windows.go` |
| 每次改动一条命令发布 | `scripts/ship.sh --bump patch\|minor\|major "说明"`：预检（在 main、树干净、不落后远端、新版本码大于线上历史最大值）→ 升 `VERSION` 并提交 `Release X.Y.Z` → 推送 → **等这个提交的 CI 绿** → `release.sh` → 验证旧版被提供新版、新版是最新。`--dry-run` 只打印计划 | `scripts/ship.sh`、`docs/release.md` |
| 发布 0.2.0 | 含阶段 1 的全部安全改动（默认开认证、配对码、首次连接指纹核对、限流、撤销、恶意主机上限、原子写、`-listen`）和主页更新按钮 | 线上 release-publish |
| 记忆 | 记录"每项改变行为的改动就发布一个新版本；仅文档 / CI / 测试的提交不发" | 项目记忆 |

约定的解释：你说"针对每次修改发布新版本"，我理解为**每次改变程序行为的改动**。只改文档、CI、测试的提交，exe 没变，发布只会产生内容相同的新版本号，所以不发。如果你想连文档提交也发，告诉我。

## 3. 验证（实际跑过的）

- 本地：`gofmt`、`go vet`、`GOOS=windows go vet`、`go test -race ./...` 全绿；UI 布局测试覆盖新按钮的命中区域，并断言它不压到列表行、日志按钮和表单字段。
- CI（linux + windows-latest）在版本提交 `2c34315` 上通过，脚本才发布。
- **独立验证（没有只信脚本自己的检查）**：临时探针用真实 `internal/update` 代码、**默认服务地址和内置公钥**，假装是 0.1.0：检查到 0.2.0，下载 19,262,976 字节并验签，sha256 与本地 `build/go-nx.exe` 逐字节一致；假装是 0.2.0 时显示 `Up to date`。`relhub check`：code 100 → 退出码 10（有更新），code 200 → 0。探针已删除，工作区干净。

### 没有验证的

- **主页按钮的绘制、点击和两次点击确认没在 Windows 上运行过**（只有布局单测和编译 / vet），见 `ACCEPTANCE.md` H18。
- **Windows 上替换 exe 并重启**（H2）仍未验证。现在可以直接用真实版本验证：装着 0.1.0 的机器 → 托盘更新项 → `Restart to update to v0.2.0`。
- 0.2.0 的新界面（H13–H17）同样没在 Windows 上跑过。

## 4. 你需要知道的

1. **更新到 0.2.0 会改变行为**：没设置过 `require_auth` 的主机会要求认证；新设备要用主机显示的 6 位码配对；第一次连一台主机要核对 ID。如果你靠"默认开放"从别的 PC 连这台，更新后要先配对一次。
2. **0.1.0 不会自动换成 0.2.0**：它需要你点托盘里的更新项（它的窗口里没有按钮）。
3. 发布出去的版本不可覆盖。新界面没经过 Windows 实机，如果 0.2.0 有问题，修复要发 0.2.1，必要时 `relhub yank` 撤回 0.2.0。

## 5. 遇到的问题

| 问题 | 处理 |
|---|---|
| `ship.sh` 最初用 `relhub check -code 99999999` 取线上最新版本号，结果它回显的是我传入的 code，预检把所有版本都判成"不比线上新" | `--dry-run` 当场暴露；改为读 `relhub list` 的 CODE 列取最大值（含已撤回的，因为版本码不可复用），并在内联命令里测过空表和比较逻辑 |
| 测试 `ship.sh` 时我用 `git stash -u`，把脚本自己也收起来了 | 只是测试方式错了，`stash pop` 完整恢复；之后先提交再在干净树上 dry-run |
| 发布期间 `release.sh` 要求工作区干净 | 脚本运行时我不碰仓库文件，文档修改放到发布完成之后 |
| `Release 0.2.0` 的 CI 挤掉了前一个提交的运行（`cancel-in-progress`） | 前一个只是文档 + 脚本修正，已被后一个运行覆盖；这也是为什么发布前要等**版本提交自己**的 CI |
