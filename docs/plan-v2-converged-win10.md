# NSU 方案收敛版 v2：放弃 Windows 7 后的架构简化
### 决策文档 —— 从"能做"收敛到"最小可行且可交付"

| 项目 | 内容 |
|---|---|
| 版本 | v2.0（取代 v1.0 报告中所有 Win7 相关结论） |
| 日期 | 2026-10-24 |
| 前提变更 | 被控端与主控端**仅支持 Windows 10 / 11（x64）**，不再兼容 Windows 7/8.x |
| 净效果 | **删掉一整套驱动栈 + 一套双实现 + 一类平台风险**；工期 −35%，成本 −45%，技术不确定性从"高"降到"中低" |
| 一句话 | 从"分块差分 + 驱动采集"收敛为"**DDA/WGC 采集 + 双编码器 + QUIC 传输 + 零内核驱动**"，Go 单栈端到端 |

---

## 1. 这一刀砍掉了什么（收益清单）

放弃 Win7 不是"少一个平台"，而是**砍掉三条独立的技术栈**：

| 被砍掉的东西 | 原成本 | 为什么它是"一整条栈" |
|---|---|---|
| **内核 Mirror Driver**（脏矩形采集） | 4 人月 + 签名流程 + 长期维护 | 内核态 = 蓝屏风险、杀软高危特征、WHQL/EV 签名、每个 Win 版本回归测试。**这是 v1.0 里最大的单点风险（R2/R3）** |
| **GDI 免驱回退路径**（BitBlt + 全帧比对） | 2 人月 + 持续性能调优 | 为客户"禁装驱动"准备的降级路径，性能差 3–5 倍，却要保证功能对等 |
| **双工具链双实现**（Go 1.20 for Win7 / C++ v142 for Win7 + 一致性测试） | 6 人月 + 永久 CI 负担 | 因 Go≥1.21、Rust≥1.78、VS2022 均已不支持 Win7 而被迫引入（见 v1.0 §6.1） |
| **Win7 特有的硬件编码兼容矩阵** | 2 人月 | Win7 下的 QSV/NVENC 驱动版本极老，几乎全是坑，且无法依赖 |
| **Win7 测试矩阵 / 老 IE / .NET 版本 / 签名测试机** | 3 人月 | 需要长期保留物理机与镜像 |
| **合计** | **≈17 人月 + 一个不可控风险** | — |

**同时解锁的能力**（Win7 上根本做不到的）：

| 新能力 | 依赖 | 产品价值 |
|---|---|---|
| 硬件编码零拷贝（D3D11 纹理直送 NVENC/QSV/AMF） | Win10 + 现代 GPU | 大动态场景码率/延迟双降，CPU 占用降到个位数 |
| WGC 单窗口采集 | Win10 1803+ | 只抓某个工控窗口（不泄露桌面其他内容），天然适合"只授权看某个 HMI" |
| IddCx 虚拟显示器（**用户态驱动**） | Win10 1607+ WDDM2.0 | 隐私屏、无头采集、任意分辨率/多虚拟屏 —— 且**用户态驱动不会蓝屏** |
| 当前 Go 工具链（1.21+） | Win10+ | 单语言端到端，无 EOL 工具链，安全补丁可持续 |
| Wi-Fi/有线切换不掉线 | QUIC 连接迁移 | 车间移动运维的真实痛点 |

## 2. 收敛后的架构（v2）

```
┌──────────────────── 被控端 Host（Win10 1809+ / Win11, x64）────────────────────┐
│  nsu-hostd.exe  (Go, 单文件, 无内核驱动, 免重启安装)                            │
│   ├─ 会话/权限/审计      ├─ 发现与配对 (mDNS + 二维码 + QUIC 证书指纹)          │
│   ├─ 输入注入 (SendInput / SendSAS / 可选 HID)                                  │
│   └─ 控制面 (本地 Web UI :随机端口, 仅 127.0.0.1)                                │
│                                                                                 │
│  nsu-engine (Go + C++ shim ~2k LOC, 同一进程内 cgo)                             │
│   ├─ capture : DXGI DDA（主）｜ WGC（单窗口/特殊窗口）                           │
│   ├─ analyze : 64×64 tile → xxHash → 脏集 → 内容分类 → 质量债                    │
│   ├─ encode  : ① 无损 tile 编解码（调色板+RLE+LZ4，CPU）                        │
│   │            ② 硬件视频（H.264/HEVC/AV1，FFmpeg hwaccel，4:2:0，intra-refresh）│
│   └─ packetize: 帧组装 + 优先级 + FEC                                            │
│                                                                                 │
│  transport: QUIC (quic-go) 单连接多流                                            │
│   ├─ 控制流（可靠）  ├─ 输入流（可靠, 最高优先级）                                │
│   ├─ 媒体流（QUIC DATAGRAM, 不可靠, 自研 FEC + CC）                              │
│   └─ 批量流（文件/剪贴板, 可靠, 限速）                                           │
└─────────────────────────────────────────────────────────────────────────────────┘
                              ▲ 局域网 P2P（mDNS 发现 / 手动 IP / 离线配对包）
                              ▼
┌──────────────────── 主控端 Client（Win10 1809+ / Win11, x64）──────────────────┐
│  Go UI (Win32/DirectComposition) + D3D11 渲染 + FFmpeg 硬解/软解                │
│  本地光标预渲染 · 整数倍/ Lanczos 缩放 · 多屏映射 · 会话恢复                     │
└─────────────────────────────────────────────────────────────────────────────────┘
```

**与 v1.0 的差异，逐项对照：**

| 层 | v1.0（含 Win7） | v2.0（Win10+） | 变化性质 |
|---|---|---|---|
| 采集 | DDA + WGC + **Mirror Driver** + **GDI 回退** | **DDA + WGC** | 少两条路径，且拿到"免费脏矩形" |
| 编码 | 4 条路径（无损 / JPEG444 / JXL / 硬件视频） | **2 条路径**（无损 tile + 硬件视频） | 复杂度腰斩 |
| 渐进精化 | 需额外有损编码器支撑 | **用无损 tile 的"半分辨率 + 8bit 深降"两遍实现**，零新增编码器 | 复用现有能力 |
| 传输 | 自研可靠 UDP（KCP 思路）+ 自研加密 | **QUIC**（DATAGRAM + 自定义 CC） | 少写 3 个子系统（可靠传输/握手/TLS） |
| 语言 | Go（Win10+）+ C++（Win7）双实现 | **Go 单栈 + C++ 薄 shim** | 少一套实现与交叉测试 |
| 驱动 | 内核 mirror driver（必需） | **无内核驱动**；IddCx 虚拟屏为**可选用户态模块** | 蓝屏风险归零 |
| 交付形态 | 需管理员 + 驱动安装 + 重启 | **单 exe / MSI，普通权限可运行** | 部署阻力大幅下降 |

## 3. 三个必须现在定死的架构决策（ADR）

### ADR-1：传输层用 QUIC，而不是自研可靠 UDP

| 维度 | QUIC（quic-go） | 自研 UDP |
|---|---|---|
| 开发量 | ~2 人月（只需写媒体调度 + FEC + CC） | ~5–6 人月（握手/加密/重传/流控/CC 全自写） |
| 加密 | TLS 1.3 内建（Go 纯用户态，不依赖 SChannel） | 需自接 Noise/TLS，且要自己做 0-RTT |
| **连接迁移** | ✅ 内建（换 Wi-Fi/IP 不断连） | ❌ 需自研 |
| 多路复用 | ✅ 原生多流 + 独立优先级 | ❌ 自研 |
| 不可靠传输 | ✅ RFC 9221 DATAGRAM | ✅ 天然 |
| 拥塞控制 | quic-go 支持**可插拔 CC**（可注入 GCC 类低延迟算法） | 完全可控 |
| 风险 | DATAGRAM 的"过期即弃"语义需自行在应用层实现；CC 需调优 | 全自我负责，工期与 bug 面大 |

> **决策：QUIC。** 唯一必须补的是"媒体流不做可靠重传、按截止期丢弃"的应用层语义，以及一个针对低延迟调优的 CC（先 CUBIC/BBR 兜底，再用延迟梯度替换）。用 TCP/UDP:443 端口形态还能穿透绝大多数企业防火墙——这在工控现场是实打实的部署优势。

### ADR-2：编码只用两条路径

| 路径 | 触发条件 | 实现 | 典型码率 |
|---|---|---|---|
| ① **无损 tile**（默认，覆盖 90% 时间） | 文本/表格/线框/色块/UI | 调色板 + RLE + 帧级 LZ4，**纯 CPU，不依赖 GPU** | 静止 5–15 kbps；操作 20–300 kbps |
| ② **硬件视频** | tile 连续 3 帧变化面积 >30%（视频预览、3D、摄像头、动画曲线） | FFmpeg + NVENC/QSV/AMF/AV1，4:2:0，intra-refresh，MB 对齐合并矩形 | 1–8 Mbps @1080p30 |

**为什么砍掉 JPEG/JXL 4:4:4 路径**：工控内容里"照片类"极少（有的话基本是摄像头画面 → 走路径②）。多一条路径 = 多一套质量调参 + 多一组回归用例，收益不成比例。**保留接口，实现留空。**

**渐进精化（v2 简化版）**：大区域突变时先发 1/2 或 1/4 降采样的无损 tile（字节数 ÷4 或 ÷16），用户立刻看到轮廓；空闲时按 4 个象限逐级补全到全分辨率。**不需要任何新编码器**，纯调度。

### ADR-3：Go 主体 + 一个薄 C++ shim（不写 Rust，不写双栈）

| 模块 | 语言 | 理由 |
|---|---|---|
| 服务/会话/发现/配对/传输/调度/协议/UI | **Go** | 并发模型、网络栈成熟、单二进制交付、交叉编译 |
| D3D11 采集（DDA/WGC）、纹理读回、光标合成 | **C++17 shim ≈ 2–3k LOC** | Go 做 COM/D3D vtable 调用极其痛苦且易错 |
| 硬件编解码 | **FFmpeg（LGPL 动态链接）** | 一套 API 覆盖 NVENC/QSV/AMF/AV1，免去逐厂商代码 |
| 未来 IddCx 虚拟屏 | C++ 用户态驱动（WUDF） | 可延后到 v1.2 |

> 若团队更熟 Rust：把 shim 换成 `windows-rs` 亦可，接口不变。**关键是把 C++ 面积压到 3k 行以内**，避免陷入"两套业务逻辑"。

## 4. 修订后的 SLO（更严，因为平台更强）

| 编号 | 指标 | v1.0 目标 | **v2.0 目标** | 收紧理由 |
|---|---|---|---|---|
| S1 | 空闲码率 | ≤20 kbps | **≤ 10 kbps** | DDA 给真脏区，无需全帧扫描 |
| S2 | 稳态操作码率 | ≤300 kbps | **≤ 150 kbps** | tile 更准 + 缓存复用 |
| S3 | 趋势曲线滚动 | ≤2.5 Mbps @10fps | **≤ 2 Mbps @15fps** | 可用硬件视频路径兜底 |
| S4 | 大动态 | ≤8 Mbps @1080p30 | **≤8 Mbps @1080p60 / ≤20 Mbps @4K30** | 硬件编码零拷贝 |
| S5 | 端到端延迟 | P95 ≤120 ms | **P95 ≤ 100 ms（30 fps 时可 ≤60 ms）** | 硬编 + 零拷贝少 15–20 ms |
| S6 | 输入回显 | ≤150 ms | **≤ 100 ms** | — |
| S7 | 弱网（1 Mbps/80 ms/1%丢包） | ≥12 fps | **≥15 fps** | FEC + 更快的恢复 |
| S8 | 文本保真 | 逐像素一致 | **同（无损为默认，非可选）** | — |
| S9 | 告警色 ΔE2000 | ≤1.0 | **≤1.0** | — |
| S10 | 被控端 CPU（稳态） | ≤5% | **≤3%** | DDA 零拷贝 |
| S11 | 首帧 | ≤1.5 s | **≤ 800 ms**（0-RTT 复用 ≤300 ms） | QUIC 0-RTT |
| S13 | **新增**：Wi-Fi↔有线切换 | — | **不断连、≤1 s 恢复** | QUIC 连接迁移 |
| S14 | **新增**：4K / 双 4K | — | 4K30 可操作、双 4K 静态可读 | 硬编 + tile |

## 5. 修订后的风险登记册（对比 v1.0）

**已消除**：R1 工具链（Go≥1.21 正好要求 Win10）、R2 驱动签名、R3 内核驱动杀软误报、R4 独占全屏（DDA 天生支持）、R14 部分老旧 DPI 怪象。

**仍存在或新增**：

| ID | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| N1 | **UAC 安全桌面 / 登录界面抓不到**（DDA 与 WGC 都不行） | 高 | 中 | 用"UIAccess=true 的签名进程"或 IddCx + 服务侧合成；**MVP 明确写进能力边界**，不做超纲承诺 |
| N2 | DDA 在混合显卡 / 外接 eGPU / HDR 切换时 `ACCESS_LOST` | 高 | 中 | 自动重建采集会话 + 状态机健壮性；72h 老化测试覆盖 |
| N3 | WGC 黄框、最小化窗口、受保护内容（DRM/银行/部分工控 HMI 可能设 `WDA_EXCLUDEFROMCAPTURE`） | 中 | 中 | 提供"单窗口模式"与"整屏模式"两套；对 `EXCLUDEFROMCAPTURE` 明确报错提示 |
| N4 | quic-go 的 CC 对"低延迟 + 高突发"调优不足 | 中 | 高 | 自定义 CC 接口注入延迟梯度算法；用 netem 做 4 档回归 |
| N5 | 硬件编码器质量差异（QSV 的 B 帧/质量档、AMF 的文本糊） | 中 | 中 | 只对"视频类区域"启用；文本区永不进硬编；按 GPU 型号做质量预设表 |
| N6 | AV1 硬编兼容性碎片化（RTX40/Arc/RDNA3 之外无） | 中 | 低 | AV1 仅作"可选增强"，默认 H.264/HEVC |
| N7 | 无驱动 → 无法实现真"隐私屏" | 高 | 低 | v1.2 用 IddCx（用户态，无蓝屏风险）补齐；MVP 用"关闭物理输出"近似 |
| N8 | 客户现场仍跑 Win10 22H2 且已过支持期（2025-10 已 EOL） | 高 | 低 | 支持策略：**主推 Win10 LTSC 2021 / IoT LTSC 2021（支持至 2032）/ Win11**；22H2 为 best-effort |

## 7. 收敛后仍然"不能省"的三件事

放弃 Win7 不会让这些变简单，它们是产品护城河所在：

1. **内容分类 + 无损文本路径**（决定低带宽画质）—— 唯一真正的技术壁垒，竞品都没有做对的；
2. **变化驱动 + 截止期调度**（决定弱网体验）—— 不是"帧率越高越好"，而是"该发的先发，过期的直接丢"；
3. **无中心发现/配对/鉴权**（决定"无中心"是不是真的）—— 这是与 RustDesk/向日葵的结构性差异。

## 8. 仍然建议"不要"做的事

| 不做 | 理由 |
|---|---|
| 包一层 RDP | 拿不到改造权，且连接即抢占现场会话 |
| 做"纯 H.264 全帧"模式作为主路径 | 低带宽下文本必糊，等于自废武功 |
| 现在做多会话虚拟桌面 | 需 IddCx + 会话隔离，与"单现场单操作员"的主流需求不匹配 |
| 兼容 RFB/VNC 协议 | 曾经是"回退路径"的理由（Win7 驱动风险）；现在驱动风险消失，兼容性成了纯负担 |
| Win10 家庭版深度适配 | 工控现场几乎全是专业版/LTSC；家庭版仅 best-effort |

## 9. 一句话总结

> **放弃 Win7 让这个项目从"可行性 3.8/5、工期 12 个月、成本 320 万、最大风险是不受控的内核驱动"变成"可行性 4.4/5、工期 7–8 个月、成本 155 万、最大风险是可控的软件健壮性"。**
>
> 收敛的本质不是"少做一个平台"，而是**把三条独立技术栈（驱动栈、双语言栈、老硬件兼容栈）合并成一条现代 Windows 图形栈 + QUIC 传输栈**。剩下的工作高度聚焦在真正产生差异化的地方：分块内容感知编码与低带宽调度。
