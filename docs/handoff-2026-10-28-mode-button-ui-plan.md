# 交接：严格 / 开放模式按钮（0.3.0）与 UI 重设计方案

- 日期：2026-10-28（KST）
- 用户的要求：① 一个按钮，默认严格（需要验证），可切到无验证的开放模式；切回严格时，原本在开放模式下进来的连接立刻失效；做过严格认证的不受切换影响。② 计划大幅更新 UI，只写设计文档；技术栈要少依赖、超高性能，外观对齐现代远控应用
- 前置：用户报告已完成更新到上一个版本（0.2.0），没有提供细节，所以 `ACCEPTANCE.md` 里的实机项仍标"待验证"
- 提交：`a570c09` 模式按钮、`118a2ae` UI 设计文档、`Release 0.3.0`（脚本生成），以及本次收尾的文档提交
- 发布：go-nx `win-x64` **0.3.0（versionCode 300）**，18.4 MiB，sha256 `23d61efc654f7ea6359dc99c968ae8388ea6984a20feb110a0551b8b54387c1a`

## 1. 模式按钮（已实现、已发布）

行为：

| 操作 | 结果 |
|---|---|
| 默认 | **严格**：新设备要配对（6 位码）或输入主机密码 |
| 严格 → 开放 | 按钮变红并提示 `Click again: anyone will be able to control this PC`，第二次点击才生效；开放时按钮常红 `OPEN mode: no verification!` |
| 开放 → 严格 | **立即生效**；消息行提示 `Ended N session(s) that were not verified` |
| 已配对的设备 | 在两种模式下都是"已验证"，**切换不受影响** |
| 开放模式下进来的陌生人 | 标记为"未验证"，切到严格时被 `CloseUnverified`(7) 断开，查看器给出说明 |
| 开放模式下配对 | 仍然可用，可以先配对再切回严格 |

我对"原本在无验证模式下的主机会立刻失效"的理解：**因开放而放进来的、未验证的控制连接**被立刻断开。如果你指的是别的东西（比如已保存的主机条目），请告诉我。

实现要点：

- `trust`：新增判决 `AllowedOpen`（因开放放行、未验证）和 `Verdict.Admitted()`。已配对设备无论哪种模式都是 `Allowed`。新建的 `Policy` 默认严格（失败即关闭）。
- `remote.Sessions`：记录每个在线会话是否经过验证；`DropUnverified` 在切到严格时断开未验证的；`add()` 在同一把锁里复查严格状态，**切换瞬间正在被放行的会话要么被拒绝，要么及时登记后被断开，不会漏过去**。
- 界面：原来的复选框换成按钮，三种状态的文字有"装得下"的测试（并做过变异检查）。

## 2. UI 重设计方案（只有文档）

`docs/ui-redesign.md`。要点：

- **继续用 Ebiten，自研极简 UI 层，不新增任何第三方模块。** 评估了 Gio、Wails/WebView2、纯 Win32+Direct2D、libw2k、Fyne；只有对 Ebiten 的判断有本仓库和 Ebiten 源码的依据，其余是经验判断，文档里都标了。
- 现状事实：UI 是绝对坐标矩形 + 文字，内嵌字体只含拉丁字母（**现在界面显示不了中文**），窗口可见时固定 60 TPS 持续重绘。
- 设计：设计令牌（配色的文字对比度我用脚本算过，均 ≥ 4.5:1）、保留式控件树 + 脏标记 + 缓存的 UI 层纹理、SDF 着色器画圆角 / 阴影、系统字体运行时加载（不内嵌 CJK）、BGRA 通道交换改到着色器里做、会话中悬浮自动隐藏的工具条、逐设备撤销列表、首次连接核对页的正式版。
- 性能预算是**目标**，不是实测：空闲 CPU < 0.3%、会话中每帧最多 2 次 `DrawImage`、零新增模块等；先做 U0 基线测量。
- **一个我必须说清的风险**：Ebiten 的按需渲染模式 `FPSModeVsyncOffMinimum` 在 v2.5 起被标为已弃用（v2.10.5 里仍存在），官方推荐的替代是 `SetScreenClearedEveryFrame(false)` + 跳过绘制。方案里把"先验证它在当前版本能用、不行就降级"作为 U0 的第一项。
- 另一个风险：Ebiten 没有 IME 组合态 API，也不暴露 UI Automation（屏幕阅读器读不到）；文档里写成了已知限制，并把纯 Win32 + Direct2D 列为长期备选。

## 3. 验证（实际跑过的）

- 本地：`gofmt`、`go vet`、`GOOS=windows go vet`、`go test -race ./...` 全绿；新测试连跑 25 次 `-race`。
- 真实 QUIC 回环测试：已配对和未配对两个查看器同时连着，主机切到严格，**只有未验证的那个被断开**（收到 `CloseUnverified`），已配对的继续；切换瞬间的放行竞态有单独的测试。
- CI（linux + windows-latest）在功能提交和版本提交上都通过，脚本才发布。
- 独立验证：真实客户端代码、默认服务地址和内置公钥，假装 0.2.0 检查到 0.3.0，下载 19,273,728 字节验签通过，sha256 与本地构建一致；假装 0.3.0 显示 `Up to date`。

### 没有验证的

- **模式按钮的绘制、点击、二次确认没有在 Windows 上运行过**（`ACCEPTANCE.md` H19）。
- UI 方案里所有性能数字都是目标，U0 之前没有任何测量。

## 4. 遇到的问题

| 问题 | 处理 |
|---|---|
| 批量替换脚本又在一步中止（gofmt 把结构体字段对齐改宽，旧文本对不上） | 先 `grep` 看哪些已落地，再从断点续做。这是第三次遇到同一类问题，经验已在 `context-recovery.md` |
| 文字可用宽度算漏了圆点后的 8 px 偏移，测试边界偏松 | 抽出 `modeTextWidth()` 统一给绘制和测试用；对一个过长标签做变异检查，确认测试会失败 |
| 查 Ebiten 的按需渲染时发现它已弃用 | 没有照着旧印象写进方案，如实写成风险和 U0 的验证项 |
