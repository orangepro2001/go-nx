## 3. 更正了 v1 的错误

| v1 说的 | 实际 | 依据 |
|---|---|---|
| "Ebiten 没有 IME 组合态 API" | **有**：`exp/textinput`（实验性，API 可能变；`Field` 已弃用，用 `Composer`），Windows 走 IMM32，支持预编辑文本和候选窗定位（`CaretBounds`）；窗口默认禁用 IME，文本输入会话才启用 | Ebiten v2.10.5 源码 |
| 会话工具条显示"已验证" | 含义不清：控制端只知道主机身份是否已核对，不知道主机怎么看自己。改为"主机已核对"；"已验证 / 未验证"只出现在被控端的会话列表 | 设计复核 |
| （没写）界面能不能用中文 | **现在不能**：内嵌字体没有 CJK 字形；Ebiten 默认关 IME 而 go-nx 没用 `textinput`；`Wrap` 只按空白断词，无空格的中文句子不会换行 | 代码与 Ebiten 源码 |

## 4. 这次从源码里查实的事实（都写进了文档）

- `NewGoTextFaceSource` 收到同时实现 Read/Seek/ReadAt 的对象（`*os.File` 满足，我写了一个编译期断言验证过，已删除）时按需读取；否则 `io.ReadAll` 整个字体读进内存。中文、韩文系统字体都是 MB 级文件，所以字体必须用 `*os.File` 打开、按需加载。
- Ebiten 的 `Key` 枚举没有 Hangul / Hanja，所以 한/영 键转发不了；方案是工具条按钮发送 `VK_HANGUL` / `VK_HANJA`，加上绕开输入法的"发送文本"。
- go-text/typesetting 的 `segmenter` 有 UAX#14 断行和字素簇迭代器，已在模块图里（Ebiten 的文本栈依赖同一个模块），不是新依赖。
- `quic.Conn.ConnectionStats().SmoothedRTT`、`ebiten.SetFullscreen`、`SetCursorMode` 都存在，go-nx 一个都没用。
- Ebiten 源码里没有 UI Automation 相关代码（我最初的 grep 命中了英文单词 "accessible"，逐条看过确认是误报）。

## 5. 没有验证的

- 文档里**所有性能数字都是目标**，没有测量。
- 字体文件名（`msyh.ttc`、`malgun.ttf`、`segoeui.ttf`）是【推断】；U0 要在 `windows-latest` 和你的 PC 上核对存在与否、大小。
- `exp/textinput` 在中文、韩文输入法下的真实表现、会话中本地 IME 关闭时按键是否原样转发、`VK_HANGUL` 能否切换远端输入法，都没有试过；后两项需要装有韩文输入法的机器（会改系统设置，标为用户自行择机）。
- 术语表是草案，**韩文必须由母语者校对**；标"（待校）"的是我把握较小的。
