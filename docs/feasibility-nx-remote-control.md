## 0. 摘要与核心结论

### 0.1 一句话结论

> 你想要的不是"NX 协议"，而是 NX 协议背后的**信息论优势**：只传"变化的最小语义单元"。这个优势在 Windows 上无法通过 X11 协议代理获得，但可以通过**分块差分 + 内容分类 + 多编码器自适应**在工程上复现 80% 的收益，代价是更大的采集/编码工程量，以及 Windows 7 上必须自研显示驱动。

### 0.2 五个关键判断

| # | 判断 | 影响 | 置信度 |
|---|---|---|---|
| J1 | RDP 是"最接近你目标"的成熟产品，但**不可改造**（协议闭源、无 P2P、绑定 Windows 会话栈、无 Win7 服务端能力优势） | 只能作为体验标杆与兜底方案 | 高 |
| J2 | 视频串流（Sunshine/Moonlight/Parsec）在**低带宽**场景是错误的技术方向：全帧 H.264 + 4:2:0，工控文本/告警色必然糊；且 Sunshine 强依赖 DXGI DDA（Win8+），Win7 直接不可用 | 只能借鉴其**传输层与拥塞控制**，不能借鉴其编码策略 | 高 |
| J3 | VNC 系（Tight/ZRLE + TurboVNC）在**低带宽静态画面**上与你的目标最接近，但其编码是"逐块独立、无内容感知、无时间维预测"，遇到趋势曲线滚动/动画即崩塌 | 是最好的**起跑线**，不是终点 | 高 |
| J4 | NX 的五大机制中，**只有 X11 语义代理（Agent）不可移植**；差分缓存、分块、自适应编码、会话保持、速率整形全部可移植 | 决定架构：做"NX 风格"，不做"NX 兼容" | 高 |
| J5 | Windows 7 是**最大工程风险点**：无 Desktop Duplication API、无 IddCx 虚拟显示、内核驱动需签名（Win7 x64 强制）、DWM 关闭时抓屏路径完全不同 | 需在项目立项时就把 Win7 路径定为"驱动 + 兼容层"独立工作流，不能当"顺手兼容" | 高 |

### 0.3 建议的最终技术路线（详见第 5 章）

```
被控端(Host Agent, Windows Service)
  ├─ 采集：Win8+ DXGI DDA ／ Win10 1803+ WGC ／ Win7 Mirror Driver(GDI 挂钩)
  ├─ 分析：64×64 分块 → 哈希 → 脏块集合 → 内容分类(文本/图形/照骗/视频)
  ├─ 编码：Lossless(调色板+RLE+LZ4) ｜ Lossy-4:4:4(JPEG/JXL/H.264-I444) ｜ Video(H.264/HEVC 硬编)
  └─ 传输：UDP + FEC + NACK + 延迟梯度拥塞控制（输入通道独立高优先级）
主控端(Client)
  ├─ 解码/合成 → 直显（D3D11 / Win7 D3D9Ex 回退）
  └─ 无中心发现：mDNS/SSDP + 二维码配对 + 手动 IP；可选离线配对包跨网段
可选：Rendezvous/中继（默认关闭，纯内网部署不启用）
```

### 0.4 可行性总评分

| 维度 | 评分(1-5) | 说明 |
|---|---|---|
| 技术可实现性 | 4 | 各子系统均有公开可验证的实现路径，无原理性障碍 |
| 低带宽性能潜力 | 5 | 分块差分 + 无损文本块，静态 HMI 可压到 <100 kbps |
| Win7 兼容 | 3 | 需自研/复用 mirror driver，签名与杀软是长期成本 |
| 工程成本可控性 | 3 | 全栈自研约 6-8 人·年起步；混合方案可降到 3 人·年 |
| 商业差异化 | 4 | 无中心 + 低带宽 + 工控语义（审计/多观众/会话保持）确有空白 |
| **综合** | **3.8 / 5** | **建议立项，但走"混合实现 + 分阶段 PoC 门禁"路线** |

## 1. 需求定义与场景建模

### 1.1 场景澄清（本报告采用的假设，需你确认）

工控远程控制与"远程办公/游戏串流"的负载特征**根本不同**，这一点决定了所有技术选型：

| 特征 | 工控 HMI / 组态软件 | 远程办公 | 游戏串流 |
|---|---|---|---|
| 画面内容 | 2D 矢量图形、表格、趋势曲线、少量位图 | 混合 | 全 3D 实时 |
| 变化面积占比 | 常态 **0.1%–3%**；切换画面时 100% | 5%–30% | 60%–100% |
| 时间相关性 | 低（画面静止数秒~数分钟） | 中 | 极高 |
| 色彩/文本保真要求 | **极高**（告警红/黄、位号、数值必须像素级可读） | 中 | 低 |
| 帧率需求 | 5–15 fps 足够，事件驱动 | 15–30 fps | 60 fps |
| 延迟敏感点 | **输入回显**（点按钮到响应） | 光标跟手 | 端到端 <40ms |
| 典型分辨率 | 1366×768 / 1920×1080 / 双屏 | 1080p–4K | 1080p–4K |
| 带宽现实 | 现场 4G 路由 / 无线网桥 / 跨厂区 VPN：**0.5–4 Mbps 共享** | 家庭宽带 | 10–50 Mbps |
| 硬件 | 老旧工控机、集显、无独显、**可能禁装驱动** | 现代 PC | 高端 GPU |

**关键推论**：这是一个"**低频次、小面积、高保真、强延迟敏感**"的负载。它天然适合**分块差分 + 无损/近无损编码**，天然不适合**全帧视频编码**。这正是 NX / VNC-Tight 类方案的舒适区，也是 H.264 全帧方案的死区。

### 1.2 把"性能第一"翻译成可验收的指标（SLO）

没有量化就没有"性能第一"。建议直接采用下列 SLO 作为设计约束与验收标准：

| 编号 | 指标 | 目标值 | 测量条件 |
|---|---|---|---|
| S1 | 空闲码率（画面静止，仅心跳+光标） | **≤ 20 kbps** | 1080p，5 分钟 |
| S2 | 稳态操作码率（点击按钮、数值刷新、小窗口重绘） | **≤ 300 kbps** | 1080p，模拟 HMI 操作脚本 |
| S3 | 中等动态码率（趋势曲线滚动、报警列表刷新） | **≤ 2.5 Mbps @ 10 fps 无损** | 1080p |
| S4 | 极端动态码率（画面整体切换、视频预览） | **≤ 8 Mbps @ 1080p30** | 允许有损 |
| S5 | 端到端帧延迟（Host 采集 → Client 呈现） | **P50 ≤ 60 ms，P95 ≤ 120 ms** | 千兆局域网，无丢包 |
| S6 | 输入回显延迟（点击 → 画面响应出现） | **P95 ≤ 150 ms** | 同上 |
| S7 | 弱网可用性（1 Mbps / 80 ms RTT / 1% 丢包） | 仍可操作，**≥ 12 fps**，无花屏拖影残留 | 使用 tc/netem 模拟 |
| S8 | 文本保真 | 12px 中文字符**逐像素一致**（无损模式下 PSNR=∞） | 与主控端截图 diff |
| S9 | 色彩保真 | 告警色 ΔE2000 **≤ 1.0** | 标准色卡 |
| S10 | CPU 占用（被控端，稳态） | **≤ 5% 单核**（静态画面） | i3-6100 级 |
| S11 | 首帧时间（点击连接到出画） | **≤ 1.5 s** | 局域网 |
| S12 | 内存占用（Host，1080p 双屏） | **≤ 200 MB** | — |

> 说明：上述数值是基于同类系统公开表现 + 本报告第 8 章性能预算推导的**工程目标**，不是实测值；PoC 阶段（第 7 章）必须实测校准。

### 1.3 隐含需求（工控场景特有，容易被漏掉，但会决定架构）

| 需求 | 为什么必须有 | 对架构的约束 |
|---|---|---|
| **多观众 / 只读监视** | 一个现场操作员 + N 个远程工程师同时看，只有一人可控 | 传输层必须支持"一路编码、多路分发"，且码率不与观众数线性增长（SFU 式扇出） |
| **会话保持（断线不锁屏）** | 现场断网/切网后重连要立刻恢复原画面 | 需要 Host 端状态缓存 + 帧序号续传；若要求"被控端锁屏后仍可见"，必须有虚拟显示驱动 |
| **审计与录屏** | 等保 2.0 / 工业控制系统信息安全防护要求 | Host 端旁路录制（复用已编码流，零额外成本） |
| **水印（含隐形水印）** | 溯源 | 需在编码前合成或编码中叠加 |
| **安全桌面 / UAC 提权窗口可见可控** | Win7 下大量工控软件需管理员运行，UAC 弹窗若黑屏＝事故 | Win10+ 需 UIAccess 签名进程或驱动；Win7 需驱动或特殊的 `Winlogon` 桌面切换处理 |
| **Ctrl+Alt+Del / SAS** | 远程重启登录 | 需 `SendSAS` API（需服务权限）或驱动级注入 |
| **多显示器 / 拼接屏 / 异形分辨率** | 工控常见 2×2 拼接、超宽屏 | 采集层必须支持整桌面 + 单屏 + 任意矩形裁剪 |
| **触摸屏 / 手轮 / 特殊 HID** | 现场触摸操作、数控手轮 | 输入层要支持 HID 级注入而非仅鼠标键盘 |
| **免驱模式** | 客户禁止装驱动/杀软白名单困难 | 必须有纯用户态降级路径（性能打折） |
| **离线可用** | 车间无外网 | 无中心发现、离线许可、无云端依赖 |

### 1.4 明确不做的事（范围边界）

- 不做跨平台（Linux/macOS/移动端）——但协议设计保留可扩展性；
- 不做公网穿透/大规模设备管理平台（MVP 阶段）；
- 不做 X11/NX 协议兼容（不实现 nxagent 互操作）；
- 不做多会话并行（RDP 式"一个 OS 多个独立桌面"）—— 除非后期引入 IddCx 虚拟显示，而 Win7 上做不到。

## 2. 技术基线：远程桌面性能的本质

在评估任何方案前，必须先建立"性能从哪来"的模型，否则容易陷入"哪个协议更快"的表面争论。

### 2.1 四段式瓶颈模型

```
[采集 Capture] → [编码 Encode] → [传输 Transport] → [呈现 Render]
      ↑ 丢帧/撕裂        ↑ 延迟/CPU      ↑ 带宽/抖动/丢包    ↑ 卡顿/缩放失真
```

每一段的物理约束：

| 段 | 关键约束 | 数量级 |
|---|---|---|
| 采集 | 拷贝带宽、GPU→CPU 回读 | 1080p 32bpp 单帧 = **8.29 MB**；60fps 原始 = **497 MB/s ≈ 4 Gbps** |
| 编码 | 单核吞吐 vs 质量 | x264 ultrafast 1080p：~150–300 fps/核（静态内容更快）；NVENC：~1–2 ms/帧 |
| 传输 | 千兆 LAN 实际可用 ~110 MB/s；WiFi/4G 更差 | 即使纯局域网，**不压缩也撑不住 30fps 4K**（4K 原始 = 2 GB/s） |
| 呈现 | 解码 + 上屏 | 硬解 3–8 ms；软解 10–30 ms |

**第一个硬结论**：任何方案都必须压缩；"局域网带宽足够所以不用压缩"是错的。压缩不是可选项，压缩策略才是竞争点。

### 2.2 码率的信息论下界（为什么 NX 类方案能赢）

设屏幕被划分为 N 个块，第 t 帧相对第 t−1 帧发生变化的块集合为 D(t)，每块编码后字节数为 b，则：

```
平均码率 R ≈ fps × |D(t)| × b / 8   (bit/s)
```

工控场景：|D|/N ≈ 0.5%，b ≈ 200–800 B（无损文本块）。

- 1080p、64×64 分块 → N = 30×17 = 510 块；变化 3 块 → 3×400 B = 1200 B/帧；10 fps → **96 kbps**。

对比全帧视频路径：

- H.264 1080p 即使"高压缩比"也要 **1.5–3 Mbps**（否则文本糊），且**每帧都要花比特**维持"不变化的背景"（P 帧 skip 虽省，但码控需保底）。

**结论：在工控负载下，分块差分方案的码率可以比全帧视频方案低 1–2 个数量级**。这就是 NX / Tight 类协议在低带宽下的根本优势，也是本项目唯一值得投入的方向。

### 2.3 延迟的构成（最小可实现值）

| 环节 | 硬件编码路径 | 软件编码路径 | 可优化手段 |
|---|---|---|---|
| 采集（含 GPU 回读） | 2–6 ms | 3–15 ms（GDI/BitBlt 更慢） | 零拷贝、GPU 内直接编码 |
| 变化检测 + 分块哈希 | 1–4 ms（CPU，多线程 SIMD） | 同 | 只用 CRC32C/xxHash，分块并行 |
| 编码 | 1–3 ms（NVENC/QSV） | 5–25 ms（x264 veryfast 1080p 增量块更快） | 增量块小 → 软件编码也够快 |
| 打包 + 传输 | 0.5–2 ms（LAN） | 同 | UDP 直发，避免 Nagle |
| 抖动缓冲 | 0–10 ms（可自适应） | 同 | 低抖动网络可设为 0–1 帧 |
| 解码 + 呈现 | 3–8 ms（硬解）/ 8–30 ms（软解） | 同 | 增量块解码几乎免费（RLE/LZ 类） |
| **合计** | **~10–25 ms** | **~25–60 ms** | 若全为无损分块，软件路径也可进 30 ms |

**关键洞察**：正因为工控的变化块**很小**，软件编码（RLE/LZ4/调色板）的绝对耗时极低（微秒级/块），反而比启动一次硬件编码会话更划算，还能避免硬件编码的固定延迟（NVENC 有 1 帧以上 pipeline 延迟）。**"小块无损 + 大块硬编"的混合调度，是这个项目的技术核心。**

### 2.4 色彩与文本：被大多数方案忽视的致命点

视频编码普遍使用 **YUV 4:2:0**（色度分辨率减半）。后果：

- 红色文字（HMI 里最常见的告警色）在 4:2:0 下会**边缘发虚、颜色偏移**，12px 中文直接不可读；
- 图形界面里的 1px 线条、单像素网格会消失或抖动；
- 渐变背景出现色带（banding）。

因此：

| 内容类型 | 必须使用的编码 | 禁止使用 |
|---|---|---|
| 文本 / 表格 / 线条图 | 无损（调色板+RLE+LZ）或 4:4:4 近无损 | 4:2:0 任何有损 |
| 位图 / 照片 / 渐变 | JPEG q80–90 **4:4:4** 或 JXL 近无损 | 4:2:0（色带） |
| 视频 / 3D / 动画 | H.264/HEVC 4:2:0 硬编 + intra-refresh | 全帧无损（带宽爆炸） |

**这是本方案与 Sunshine/Parsec/RustDesk 的根本分野**，也是竞品在工控场景被吐槽的根因。

## 3. 主流方案横向评估

评估口径统一为：**① 低带宽下的实际表现（权重最高）② Win7 服务端可用性 ③ 延迟 ④ 可改造/可嵌入 ⑤ 画质色准 ⑥ 工程与许可成本**。

### 3.1 RDP（Microsoft Remote Desktop Protocol）

**机制拆解**

| 层 | 实现 |
|---|---|
| 会话 | T.128/MCS 多通道；TCP 3389；RDP 8+ 增加 UDT/UDP 短传输（`RDP-UDP`），丢包时视频/图像可走 lossy+前向纠错 |
| 图形 | MS-RDPEGDI（GDI 绘图指令）→ MS-RDPEGFX（Graphics Pipeline，图元+Surface 命令）→ 多个编解码器叠加 |
| 编解码器 | RemoteFX（分块 + 类小波/DCT 混合，**优于 JPEG 的文本表现**）、RemoteFX Progressive（**渐进式：先粗后精**）、AVC420（H.264 4:2:0）、AVC444（H.264 4:4:4 + 色度辅助通道，Win10 起） |
| 缓存 | 位图缓存（内存 + 持久化到磁盘）、字形缓存（Glyph cache）、九宫格拉伸缓存 —— **这是 RDP 低带宽表现好的第二大原因** |
| 带宽自适应 | `Network Auto Detect`：根据 RTT/丢包动态调整帧率、色彩深度（32→16→8bpp）、关闭主题/壁纸/字体平滑 |
| 显示 | 服务端虚拟显示驱动（RDPDR/`RDPUDD`），可动态改分辨率、多显示器、RemoteApp 单窗口重定向 |

**优点**

1. **低带宽能力被严重低估**：在 1 Mbps/100 ms 下仍可办公级使用，靠的是"指令级 gfx + 持久缓存 + 动态降色深"三件套；
2. 服务端是**内核显示驱动 + 会话隔离**，能拿到"系统真实绘制语义"，天然支持会话断开保持、锁屏前画面、安全桌面；
3. 有 AVC444 —— 4:4:4 H.264，文本质量远好于 4:2:0，是"视频编码用于桌面"的正确姿势；
4. Windows 原生、零部署成本、客户端极轻。

**缺点（对本项目是致命的）**

1. **完全不可改造**：协议栈闭源（部分开源在 FreeRDP/Moonlight 侧，仅客户端），不能加"工控语义"（位号识别、告警联动、审计水印、多观众广播）；
2. **无 P2P 无中心化能力**：RDP 是"点对点直连 + 需要目标 IP/域名"，没有发现、配对、NAT 穿透、证书配对机制；无中心场景下要靠手工运维；
3. **"连接即抢占"**：连接交互式会话会把本地用户踢到锁屏（Win10 家庭版/专业版单会话），工控现场"远程看一眼"的需求直接冲突。RDPWrap/多用户补丁属于破坏许可与稳定性的黑科技，不可产品化；
4. **Win7 服务端是 RDP 7.1**：无 RemoteFX（除 Enterprise+RemoteFX 更新）、无 AVC、无 UDP 传输、无渐进式 —— 恰好是你最需要兼容的平台上最弱；
5. 授权：RDP 用于"远程管理"2 会话免费，但作为产品分发/多用户服务涉及 CAL 授权，商业上不可行。

**可借鉴**：① 渐进式编码（先粗后精）；② 位图+字形持久缓存；③ 动态降色深/降帧率作为拥塞兜底；④ 4:4:4 编码用于文本。

**结论**：**不能作为技术底座，但必须作为"体验基线"** —— 任何自研方案在 1080p HMI 场景下若明显不如 RDP，就不要发布。

### 3.2 视频串流技术（Sunshine / Moonlight、Parsec、NVIDIA GameStream）

**机制拆解**

| 环节 | Sunshine 实现 |
|---|---|
| 采集 | Windows：**DXGI Desktop Duplication API（Win8+）**；Linux：X11/NvFBC/KMS |
| 编码 | NVENC / QSV / AMF / VideoToolbox / VAAPI，或软件 x264；H.264 / HEVC / AV1 |
| 传输 | RTSP 握手 → RTP over UDP；**FEC（默认 5%–20% Reed-Solomon）+ NACK 重传**；独立控制/输入通道 |
| 延迟优化 | `zerolatency`、无 B 帧、VBV 单帧缓冲、slice 级 intra-refresh（避免 I 帧尖峰） |
| 输入 | SendInput + ViGEmBus 虚拟手柄；相对/绝对鼠标模式 |
| 音频 | Opus 低延迟 |

**优点（值得全盘借鉴的部分）**

1. **传输层是业界最佳实践**：UDP + FEC + NACK + 动态码率，局域网 1080p60 端到端 10–30 ms 可达；
2. **码率整形与拥塞控制**成熟（Moonlight 的 bitrate 固定 + Sunshine 的 FEC 自适应）；
3. 硬件编码路径完整（NVENC/QSV/AMF 全部支持），可直接复用 FFmpeg 的 hwaccel 生态；
4. 开源（GPLv3）可读可验证，架构清晰（`video.cpp`/`rtsp.cpp`/`stream.cpp`）。

**缺点**

1. **全帧 H.264 是错的方向**：1080p 静态 HMI 用 H.264 也要 1–3 Mbps 才不糊文本，且 4:2:0 色度必然损伤告警色；相比之下分块无损方案只需 100 kbps —— **差 10–30 倍**；
2. **Win7 直接不可用**：DDA 是 Win8+ 的 API，Sunshine 官方只支持 Win10+；这不是"打补丁"能解决的，是采集基座缺失；
3. 面向"一个 Client 一个 Session"，无多观众扇出设计；
4. GPLv3 传染性（若链接其代码，产品必须 GPLv3）；
5. 无会话保持、无安全桌面、无审计/水印、无发现配对机制；
6. Parsec 更极端：延迟最优但**必须联网鉴权**，与"无中心"直接冲突；且闭源。

**可借鉴**：UDP/FEC/NACK/拥塞控制、intra-refresh、硬件编码抽象层、输入通道优先级设计。

**结论**：**取其传输，弃其编码**。

### 3.3 VNC 系（RFB / Tight / ZRLE / TurboVNC / TigerVNC / RealVNC）

**机制拆解**

| 机制 | 说明 |
|---|---|
| 模型 | 客户端发 `FramebufferUpdateRequest`（增量/全量），服务端回 `FramebufferUpdate`（若干矩形）；`ContinuousUpdates` + `Fence` 扩展可做成流式 |
| Raw / RRE / Hextile / CoRRE | 原始像素 / 纯色矩形 / 16×16 子块 / 紧凑色块 —— 适合纯色 UI |
| **Tight** | 矩形 → 选过滤器（Copy / Palette / **Gradient**）→ zlib（按矩形自适应压缩级别）→ 照片区用 JPEG。**这是 VNC 系低带宽性能的主力** |
| ZRLE | zlib + 调色板 + RLE，无损，对文本/线条极友好 |
| 近年扩展 | TigerVNC 引入 H.264 矩形编码（OpenH264）；TurboVNC 强化 JPEG + 自适应级别；RealVNC 私有混合编码 |
| 安全 | VNC Auth（弱）/ VeNCrypt（TLS）/ RA2 |

**优点**

1. **天然契合工控负载**：矩形级增量 + 无损调色板编码，静态画面码率可低至 50–200 kbps；
2. **Win7 完美兼容**：纯用户态 GDI `BitBlt` 抓屏即可工作，不需要任何驱动（这是它最大的工程优势）；
3. 协议简单、实现成熟（libvncserver / TigerVNC / TurboVNC 全部开源可读）、可自行扩展私有编码；
4. 无中心、点对点、可直接 IP 连接，配对机制可自建；
5. 支持多客户端同时观看（天然广播模型）。

**缺点**

1. **无帧间/时间维预测**：每个矩形独立编码，趋势曲线滚动时"="全屏重编码"，码率瞬间冲到 5–20 Mbps；
2. **无码率控制**：只有 `throttle`（限速）与压缩级别，没有基于带宽估计的自适应调度；
3. **传输在 TCP 上**：丢包 → 队头阻塞 → 延迟抖动（这是 VNC"卡顿感"的主因，不是带宽问题）；
4. GDI `BitBlt` 抓屏在 Win8+ 上受 DWM 影响，全屏 1080p 抓取约 10–25 fps，CPU 高（~10–25% 单核），且抓不到 D3D 独占全屏、抓不到光标下的硬件层；
5. 无音频、无剪贴板/文件（需扩展）、无会话保持、无安全桌面、无审计；
6. 调色板编码对照片/渐变差（Tight 靠 JPEG 兜底，但 4:2:0 又伤色）。

**可借鉴**：① 矩形/分块增量模型；② Tight 的"过滤器选择"思想（这正是"内容分类"的雏形）；③ ZRLE 的无损路径；④ 多客户端扇出。

**结论**：**最合适的"起跑线"与 PoC 对照组**。若在此之上补齐"时间维差分 + 内容自适应 + UDP 传输"，就得到了本报告的目标架构。

### 3.4 RustDesk

**机制拆解**

| 环节 | 实现 |
|---|---|
| 语言/UI | Rust 核心 + Flutter UI；体积较大 |
| 架构 | **必须有** rendezvous（`hbbs`）与 relay（`hbbr`），可自建；支持"直接 IP 访问"（`direct-server`） |
| 穿透 | 自研 UDP 打洞 + NAT 类型探测；失败回落中继 |
| 采集 | Windows：DXGI DDA 优先，GDI 回退；`scrap` crate 抽象 |
| 编码 | VP8/VP9/AV1（软件，`vpx`/`aom`）、H.264/H.265（OpenH264 软编 + FFmpeg 硬件编码 MF/NVENC/QSV/AMF）；预设"质量/平衡/低延迟" |
| 传输 | TCP / 自研 UDP 通道；无 FEC、拥塞控制较简单 |
| 功能 | 文件传输、剪贴板、多屏、音频、录屏、地址簿、权限（键盘/剪贴板/文件） |

**优点**

1. 开源（AGPLv3）、工程完整度高、P2P 与自建服务器方案成熟 —— **是"无中心/可自建"的最佳参考实现**；
2. 跨平台覆盖全，可读性尚可，便于学习其"会话状态机 + 能力协商"设计；
3. 硬件编码接入 FFmpeg，编码器选择逻辑值得复用。

**缺点**

1. **编码策略仍是"全帧视频"**：文本/告警色在低码率下明显劣化；无分块语义层，静态画面照样吃 1–2 Mbps；
2. **上游已放弃 Windows 7/2008 R2**（社区只能自行降级工具链重建，不具备产品级可维护性）；
3. 依赖 `hbbs` 才有完整体验，"无中心"只能退化为手工 `直接IP`，无发现/配对/证书体系；
4. AGPLv3 传染性极强（SaaS 化也要开源），商业闭源不可用；
5. 延迟中等（无 FEC，拥塞控制弱），弱网抖动明显；
6. Flutter 客户端在低配/国产信创机上体验偏重。

**可借鉴**：能力协商与权限模型、P2P 打洞流程、自建 rendezvous 的部署形态、编码器选择与硬件探测。

### 3.5 NX 系（NoMachine NX 3 / NX 4+ / x2go / nx-libs）

**这是本报告的核心参照，需要拆到机制级。**

#### 3.5.1 NX 的五个核心机制

| # | 机制 | 原理 | 可移植到 Windows？ |
|---|---|---|---|
| M1 | **X11 语义代理（nxagent）** | 在服务端充当"假 X Server"，X 客户端把**绘图协议**（PolyLine/FillRect/PutImage）发给 agent；agent 在本地保留 pixmap 与"伪像素"状态，只把**语义差异**经压缩后送客户端。客户端 `nxproxy` 重建 X 协议再喂给真 X Server | ❌ **不可移植**：Windows 没有对应"显示协议"可代理；DWM/D3D 不暴露语义；GDI 挂钩只能覆盖老式 2D 应用且极不稳定 |
| M2 | **差分与缓存（NX cache）** | 图像/字形/像素图缓存复用；重复位图只传 ID；"dirty region" 只在真正变化时传 | ✅ 完全可移植（分块哈希 + tile 缓存 + CopyRect） |
| M3 | **自适应编码（link-speed 驱动）** | 按用户设定的链路带宽（modem/ISDN/ADSL/LAN）选择压缩算法与质量（JPEG 质量、RLE、调色板、zlib 级别） | ✅ 可移植，且可做得更好（实时带宽估计而非手工档位） |
| M4 | **速率限制与调度** | 带宽预算内按"重要性/时效性"调度发送，丢弃过期帧（而非排队） | ✅ 必须移植（这是弱网体验的关键） |
| M5 | **会话保持（suspend/resume）** | agent 常驻，客户端断开后状态保留，重连即续（NX 最经典的卖点） | ✅ 可移植（Host 端保持编码状态与帧缓存） |

**NX 3.5 的实测能力**：官方长期宣传"在 9600 bps–56 kbps 链路上可用"，其根因是 M1 —— X11 文本界面下，一次"打字"在协议层只有几个字节，**压缩比取决于语义而非像素**。这就是 NX 比 VNC 快一个数量级的真正原因，也是它在"图形化 Web/视频"场景并不神奇的原因。

#### 3.5.2 NX 4+（NoMachine 现役）与 NX 3 的差别

- NX 4 起**协议重写、闭源、与 NX 3 不兼容**；不再强调"X11 代理"，转向"自适应显示协议 + 图形/视频混合编码（含 H.264 硬件编码）+ UDP 传输 + 缓存"；
- 支持 Windows 作为**服务端**（用自研显示驱动/采集层，非 nxagent）；
- 换句话说：**NoMachine 自己在 Windows 上做的，正是本文第 5 章要设计的架构** —— 这从侧面证明了技术路线成立，也说明它没有"NX 语义优势"这一层。
- 商业限制：闭源、按连接/席位授权、无法嵌入、无法定制（对工控审计/水印/多观众无解）、无中文工控生态支持。

#### 3.5.3 x2go / nx-libs

| 项 | 情况 |
|---|---|
| 组成 | `nx-libs`（Arctica Project 维护的 NX 3.5.x：nxagent/nxcomp/nxproxy）+ x2go 会话管理 |
| 服务端 | **仅 Linux（X11）**；Windows 只能做客户端 |
| 许可 | **GPLv2**（含部分 X11/MIT 代码）→ 闭源商业产品链接即传染（进程边界可争辩，但法律风险不应承担） |
| 现状 | 维护活跃度低，Wayland 时代前景黯淡；性能优势仅体现在 X11 应用 |
| 对本项目价值 | **仅作为 M2–M5 的"思想参考"与算法对照，不可作为底座、不可复制代码** |

#### 3.5.4 结论

> NX 的"协议"是 X11 时代的产物，其**最大优势 M1 在 Windows 上不存在**。继续追求"用 NX 协议"会掉进一个无法交付的坑；而 NX 的**其余四个机制（M2–M5）恰恰是工控场景最需要的**，且完全可以在 Windows 上实现。

## 4. 核心论证：NX 协议能否用于 Windows？

### 4.1 NX 的收益到底来自哪里（定量拆解）

以"在 HMI 画面上点一个按钮"为例，比较三条路径传输的信息量：

| 路径 | 实际过网数据 | 说明 |
|---|---|---|
| X11 语义（NX M1） | ~40–200 B | `PolyFillRectangle` + `PolyText8` 等协议消息 |
| 分块差分 + 无损（NX M2/M3，可移植部分） | ~1–6 KB | 4–8 个 64×64 块，调色板+RLE |
| 全帧 H.264（Sunshine 路线） | ~20–80 KB（且需持续支付维持码率） | 单帧 P 帧 + 码控保守性开销 |

即：**M1 比 M2 再快 10–50 倍，但只对"由协议描述生成的画面"成立**。一旦画面来自位图贴图（现代 SCADA 的皮肤、渐变、地图底图），M1 的优势迅速消失 —— 这也是为什么 NX 在"漂亮 UI"上并不比 VNC 强。

**推论**：追逐 M1（NX 协议本体）的收益上限是"工控软件是纯 X11 时代 GUI"这一不成立的前提；而 M2–M5 的收益在 Windows 上**可以 100% 拿到**。

### 4.2 Windows 上"语义层"的替代路径评估

| 路径 | 能拿到什么语义 | 覆盖率 | 稳定性 | 合规/成本 | 结论 |
|---|---|---|---|---|---|
| **GDI/USER32 API Hook**（Detours/MinHook 注入） | 绘图调用（TextOut、BitBlt、Rectangle…） | 仅老式 GDI 应用；WPF/Direct2D/Qt-OpenGL/浏览器全部绕过 | ⚠️ 差：注入崩溃、反作弊/杀软误报、跨架构、多进程 | 高维护成本 | ❌ 不作主路径，可作"加强模式"实验 |
| **显示驱动（Mirror/虚拟显示）** | 帧缓冲 + **脏矩形**（GPU 层） | 100%（含 D3D/视频） | ✅ 稳（内核层，进程无关） | 需签名；Win7 x64 强制 | ✅ **Win7 主路径** |
| **DXGI Desktop Duplication（Win8+）** | 帧纹理 + 脏/移动矩形 | 100%（除安全桌面） | ✅ 稳 | 无驱动 | ✅ **Win8+ 主路径** |
| **Windows.Graphics.Capture（Win10 1803+）** | 窗口/显示器帧 + 光标元数据 | 高（可单窗口，含部分 DDA 抓不到的窗口） | ✅ 稳 | 无驱动 | ✅ 补充路径（单窗口/防截屏窗口） |
| **UI Automation / MSAA** | 控件树、文本、边界框 | 仅标准控件 | 中 | 无 | ⚠️ 仅用于"辅助功能"（控件树同步、无障碍、半语义优化），不作主路径 |
| **D3D/DWM 内部接口**（`DwmGetDxSharedSurface` 等） | 合成后纹理 | 高 | ❌ 未文档化、随版本变化 | 高 | ❌ 不采用 |

**关键判断**：Windows 上想要 NX M1 的效果，唯一稳定的方式是**驱动级**（SPICE 的 QXL 就是证明：靠 virtio 驱动才拿到 draw commands）。而自研"语义驱动"意味着要为每个工控软件做兼容，工程量与风险不可接受。**因此：放弃 M1，全力做好 M2–M5，并用"驱动级脏矩形"逼近 M1 的效率下限。**

### 4.3 结论：定义 NSU 协议（NX-Style Unified）

不强求与 NX 兼容，而是把 NX 的可移植内核 + RDP 的渐进式 + VNC 的分块 + 串流的传输层，融合为一个自有协议：

| NSU 层 | 来源 | 设计要点 |
|---|---|---|
| L1 采集/脏区 | Mirror Driver / DDA / WGC | 拿到"真实变化"，避免全帧比对 |
| L2 分块与缓存 | NX M2 + VNC Tight | 64×64 对齐、tile 哈希、tile 复用（CopyRect 语义）、字形/图标级复用 |
| L3 内容分类 | Tight 过滤器 + PCoIP 多编码器 | 每块判定 SOLID/TEXT/GRAPHIC/PHOTO/VIDEO |
| L4 编码 | 自研无损 + JPEG444/JXL + H.264/HEVC | 分块独立可解；大区域合并编码；**渐进精化** |
| L5 调度 | NX M4 + 串流拥塞控制 | 变化驱动 + 截止期调度 + 带宽预算 + 丢过期帧 |
| L6 传输 | Sunshine FEC/NACK + 自研 CC | UDP + FEC + NACK + 延迟梯度拥塞控制；TCP 回退 |
| L7 会话 | NX M5 | 断线保持、状态缓存、多观众扇出、审计旁路 |

**一句话**：NSU = "**NX 的省流量思想 + RDP 的渐进画质 + VNC 的工程可行性 + 串流的传输质量**"。

```
│  收包/抖动缓冲 → FEC 恢复 → 解码(按块) → 合成双缓冲 → D3D11/D3D9Ex 呈现          │
│  输入采集 → 事件打包 → 带宽/延迟探测 → 请求关键帧/精化                           │
│  多窗口 / 多显示器映射 / 缩放算法(Lanczos 或整数倍最近邻) / 光标合成            │

```

### 5.2 采集层：三条路径 + 一条回退

| 路径 | 平台 | 帧率 | CPU | 脏矩形 | 备注 |
|---|---|---|---|---|---|
| DXGI DDA | Win8+ | 60+ | 1–4% | ✅（Dirty + Move） | 需处理"显示模式切换导致 `DXGI_ERROR_ACCESS_LOST`"、混合显卡、独占全屏 |
| WGC | Win10 1803+ | 30–60 | 2–5% | ❌（需自行比对） | 可抓单窗口、可抓部分 DDA 黑屏的窗口；有黄框可去除 |
| **Mirror Driver** | Win7（及 Win8+ 可选） | 30 | 1–3% | ✅（真正脏区） | 需内核签名；这是 Win7 唯一能拿到脏矩形的方式 |
| GDI BitBlt | 全平台（免驱回退） | 8–20 | 15–30% | ❌（需全帧比对） | 客户禁装驱动时的兜底；用"分条带 CRC + 只比对变化条带"降开销 |

**必须有"全帧比对"作为最后兜底**：无论哪条路径，都要有一个"每帧对变化区域做 xxHash/CRC32C 分块校验"的独立校验器，用于检测驱动漏报的脏区（真实世界常见），并作为正确性保障。成本约 0.5–2 ms/1080p（SIMD + 多线程）。

### 5.3 分块、缓存与"变化驱动"调度（省流量的第一杠杆）

**核心原则：不按固定帧率推送，按"变化 + 截止期"推送。**

```
事件循环:
  1. 采集给出脏矩形集合 D（或全帧比对得到）
  2. 合并/外扩到 64×64 tile 边界 → 脏 tile 集 T
  3. 对每个 t ∈ T:
       h = xxHash64(pixels)   # 与 tile 缓存比对
       if h 未变: 标记 HIT，发送 tiny "copytile" 引用（或直接不发）
       else:      内容分类 + 编码 + 入发送队列（带优先级与截止期）
  4. 若当前无变化且存在"质量债"（渐进精化未完成）:
       发送精化 pass（低优先级，可被随时抢占）
  5. 若带宽预算有余且客户端请求: 发送"帧完整性校验"
```

**带宽账面（1080p，510 个 tile）**

| 场景 | 变化 tile | 单 tile 字节 | 帧率 | 码率 |
|---|---|---|---|---|
| 静止 | 0 | — | 事件驱动 | **5–15 kbps**（心跳+光标） |
| 数值刷新 / 光标移动 | 1–2 | 200–400 B | 10 | 20–60 kbps |
| 按钮点击 / 弹窗 | 4–12 | 300–800 B | 突发 | 平均 <100 kbps |
| 报警列表刷新 | 30–60 | 400–800 B | 5 | 0.5–1.5 Mbps（瞬时） |
| 趋势曲线平移 | 200–400 | 400–800 B | 10 | 4–10 Mbps（**需有损/渐进**） |
| 画面切换 | 510 | 300–900 B | 1 | 250–450 KB 一次性，**必须渐进精化** |

→ 前四行就是 90% 的时间。**这解释了为什么 S1/S2 目标（≤20 kbps / ≤300 kbps）是可达的**，而全帧 H.264 方案在此场景下限就是 0.5–1 Mbps。

### 5.4 编码层：内容分类 + 多编码器

**分类器（每 tile，8×8 子块统计）**

| 特征 | 判定 | 编码选择 |
|---|---|---|
| 单色 | SOLID | 3–6 B（颜色 + tile ID） |
| 颜色数 ≤ 256 且无渐变 | TEXT/PALETTE | 调色板 + RLE（ZRLE 式），150–600 B，**无损** |
| 高频边缘 + 中等颜色数 | GRAPHIC | 无损 RLE+LZ4；或 JPEG **4:4:4** q90 |
| 空间平滑、颜色连续 | PHOTO | JPEG 4:4:4 q80–90 / JXL 近无损；或 H.264-I 4:4:4 |
| 时间上持续变化（连续 3 帧 >30% 像素变化） | VIDEO | 合并为 MB 对齐大矩形（≥256×256）→ H.264/HEVC 硬件编码，4:2:0，intra-refresh |

**渐进精化（Build-to-Lossless，源自 PCoIP，强烈建议）**

- 大区域变化时：先发 q30–40 的快速近似（占 15% 字节），**用户 50 ms 内看到反馈**；
- 画面静止后在"空闲带宽"里逐轮精化（q60 → q85 → 无损），直到达到目标保真度；
- 效果：**交互延迟与画质解耦** —— 这是工控体验的关键，也是竞品普遍缺失的能力。

**编码器可用性矩阵（被控端）**

| 硬件 | H.264 硬编 | HEVC 硬编 | 备注 |
|---|---|---|---|
| Intel 核显 HD4000+（Win7 驱动） | ✅ QSV（Win7 驱动支持有限，需实测） | ❌（Win7 基本无） | 工控机最常见，**Win7 上 QSV 往往是坑**，需运行时探测 + 回退软编 |
| NVIDIA GTX650+ / Quadro | ✅ NVENC | ✅（Kepler 之后部分） | Win7 有驱动但版本老（如 47x 系列），NVENC SDK 版本受限 |
| AMD | ✅ AMF/VCE | 部分 | Win7 驱动老，AMF 支持差 |
| 无独显/驱动被禁 | ❌ | ❌ | 走纯 CPU 分块无损路径（工控场景恰好可接受） |

> **重要结论**：工控机大量是"Win7 + 老核显 + 禁装驱动"，因此**主路径必须是纯 CPU 的分块无损编码**，硬件编码只作为"大动态场景的加速选项"。这一点直接推翻"照抄 Sunshine 架构"的可行性。

### 5.5 传输层

**协议要点**

| 项 | 设计 |
|---|---|
| 通道 | ① 输入/控制（可靠、低延迟、小包、可 TCP 或可靠 UDP）② 视频/图像（不可靠 UDP）③ 批量（文件/剪贴板，可靠） |
| 帧结构 | `[hdr:16B][tile records...]`，支持一个 UDP 包内多 tile、一个 tile 跨包（分片重组） |
| FEC | Reed-Solomon（如 RS(10,3)，~10–30% 冗余自适应）；丢包 <0.1% 时关闭 |
| NACK | 30 ms 窗口内重传；超出截止期直接放弃，交由后续精化/关键帧修复（**不等重传**） |
| 拥塞控制 | 延迟梯度（排队延迟 >20 ms 即降码率）+ 丢包惩罚；目标 `1.1×BWE`；AIMD 快速恢复 |
| 优先级 | 输入 > 光标 > 首帧/关键帧 > 增量 > 精化 > 批量 |
| 加密 | X25519 + ChaCha20-Poly1305（Noise IK 模式）或 TLS 1.3；**必须用纯用户态实现**（Go 的 `crypto/tls` 与 `x/crypto` 为纯 Go，不依赖操作系统 TLS 栈，规避 Win7 SChannel 的 TLS 1.2/密码套件坑） |
| 连接建立 | 1-RTT 握手 + 能力协商 + 屏幕几何 + 编码能力矩阵；断开后 0-RTT 恢复（ticket） |

**为什么不用 QUIC**：Win7 无系统 QUIC 无所谓（QUIC 是用户态），但 QUIC 的可靠有序流模型对"过期即弃"的视频不友好，且实现复杂度高、调试成本大。建议：**自研轻量可靠 UDP（KCP 思路）+ 不可靠视频通道**，复杂度可控。

### 5.6 输入与注入

| 项 | 方案 |
|---|---|
| 鼠标/键盘（普通） | `SendInput`（Win7 起全支持）；绝对坐标用 `MOUSEEVENTF_ABSOLUTE` + 0–65535 归一化（注意多屏虚拟桌面坐标跨度） |
| 游戏/工控的 Raw Input | 需驱动级虚拟 HID（HIDClass 小驱动或 ViGEm 类方案）；无驱动时退化为 SendInput（部分软件不响应） |
| 触摸/多点 | `InjectTouchInput`（Win8+）；Win7 无 API → 需驱动或模拟 WM_TOUCH |
| Ctrl+Alt+Del | `SendSAS(FALSE)`（服务以 SYSTEM 运行，需 `SeTcbPrivilege` 或注册表策略） |
| UAC / 安全桌面 | Win7：驱动路径可见；Win10+：DDA 抓不到 → 需 `UIAccess=true` 的签名进程或驱动；**须在产品文档中明示能力边界** |
| 键盘布局/IME | 传递扫描码（scancode）而非虚拟键，规避布局差异；关键：`Ctrl+Alt+Del`、`Alt+Tab`、`Win` 键需显式转发策略 |
| 输入回显优化 | 客户端本地"光标预渲染 + 点击涟漪"，服务端在 30 ms 内回传确认；避免"点了没反应"的错觉 |

### 5.7 无中心发现、配对与鉴权

| 场景 | 机制 |
|---|---|
| 同网段 | mDNS `_nsu._udp.local` 广播（Host 存在性 + 指纹 + 名称）；`SSDP` 作为兼容回退；UDP 广播发现作为最后手段 |
| 跨网段/跨 VLAN | ① 手工 `IP:Port + 配对码`；② **离线配对包**（二维码/文件，含公钥指纹、候选地址、上次端口）；③ 可选局域网内一个"轻中继"（任一已连通的现场 PC） |
| 鉴权 | 设备证书（首次配对生成，TOFU + 指纹核对）+ 用户口令/PIN；支持"仅查看码""一次性授权码""永久信任" |
| 授权模型 | 每设备角色：`view` / `control` / `admin` / `record`；可设置时间窗、操作白名单 |
| 零信任增强 | 可选：仅允许指定主控端公钥连接；连接请求需 Host 侧本地确认（弹窗/物理按键） |

> 与 RustDesk/向日葵的根本差别：**不需要任何公网服务器即可完成"发现 + 鉴权 + 连接"**，这是"无中心"的实质。

### 5.8 客户端呈现

- 解码与合成在独立线程，双/三缓冲，`D3D11` 交换链（Win7 回退 `D3D9Ex`）；
- 缩放：整数倍最近邻（保锐利）或 Lanczos（保平滑），用户可切；**禁止默认双线性**（会糊文本）；
- 光标：本地合成（零延迟跟随），服务端光标作为"权威位置"低频校正；
- 多显示器：单窗口多视图 / 每屏一窗口 / 拼接视图；
- 色彩：默认 sRGB 直通，可选 ICC 映射；提供"色准模式"（无损 + 关闭一切后处理）；
- 硬解：D3D11VA（Win8+）/ DXVA2（Win7）；软解兜底（openh264/ffmpeg）。

### 5.9 控制面与会话

| 能力 | 实现要点 |
|---|---|
| 多观众扇出 | 一路编码 → N 路分发；不同客户端能力不同（分辨率/解码能力/带宽）时，按"最弱观众"编码 + 对强观众单独发精化流 |
| 断线保持 | Host 保持 tile 缓存 + 质量债表 + 帧序号；重连发"增量快照"（只发与客户端已知状态的差） |
| 审计 | 记录连接、输入事件（可脱敏）、文件传输、剪贴板；旁路录制复用已编码流（零额外 CPU） |
| 水印 | 编码前叠加可见水印（含时间/账号）；隐形水印在 YUV/像素 LSB 层，抗压缩需专门的鲁棒方案（后期） |
| 剪贴板/文件 | 独立可靠通道，限速 + 类型白名单 |
| 隐私屏 | 需驱动支持（物理屏黑屏但虚拟屏继续编码）→ Win7 用 mirror driver 可做，Win10+ 需 IddCx |

## 6. 关键难点与风险登记册

### 6.1 头号风险：工具链已经不支持 Windows 7

这是一个**容易被忽视但会推翻排期**的硬约束：

| 事实 | 后果 |
|---|---|
| **Go 1.21 起要求 Windows 10+**，Windows 7/8/8.1 支持被移除 | 用当前 Go（如 1.27）编译的二进制**在 Win7 上无法启动**（依赖 `api-ms-win-core-*`/`SetThreadDescription`/`GetSystemTimePreciseAsFileTime` 等新 API 的导入） |
| **Rust 自 1.78 起把 Windows 7 降为 Tier 3**，std 不再保证可用 | 这正是 RustDesk 官方宣布"Win7/2008R2 不再支持"的根因；社区只能锁定旧工具链 |
| **VS2022 (v143) 不再支持 Win7 目标**；VS2019 (v142) 是最后可用的 MSVC | Win7 组件必须用 v142 工具集（或 mingw-w64/clang）编译 |

**对策（三选一，建议 B）**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 全量 Go 1.20 编译 Win7 版 | 代码统一 | 使用 EOL 工具链，**无安全补丁**，长期不可接受 |
| B | **双工具链 + 分层**：协议/传输/调度用 Go（Win10+ 版本），Win7 版本用 C++17 (v142) 实现同一套协议（共享 `.proto`/IDL 与测试向量） | 主平台技术先进，Win7 可控 | 两套实现需严格一致性测试（协议 conformance test 必须有） |
| C | 全套 C++17 (v142) 单实现 | 单一代码库，Win7/10+ 同源 | 开发效率低于 Go，网络/并发代码风险高 |

> 若 Win7 是"必须有"而非"尽量兼容"，**建议 B**：把"协议 + 传输 + 编码容器"定义成与语言无关的规范（IDL + wire spec + 测试向量），Go 与 C++ 双实现，CI 做交叉互通测试。这也顺带解决"客户端也要支持 Win7"的问题。

### 6.2 风险登记册

| ID | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| R1 | Win7 工具链/运行时缺失（见 6.1） | 高 | 高 | 方案 B 双实现；Win7 目标明确写入合同与验收 |
| R2 | Mirror driver 签名门槛（Win7 x64 强制签名；企业内可用自签 + 组策略，但公众分发需 WHQL/EV） | 高 | 高 | MVP 走"免驱模式 + 可选驱动增强"；驱动做 EV 签名 + 微软 attestation；提供"驱动安装失败仍可用"的降级路径 |
| R3 | 杀软/EDR 误报（抓屏 + 注入 + 内核驱动 = 高危特征） | 高 | 中 | 代码签名、提交各厂商白名单、避免 API Hook、安装包不静默、提供企业级白名单指引 |
| R4 | 独占全屏 / D3D 程序采集黑屏 | 中 | 中 | DDA 天然支持；Win7 依赖 mirror driver；提供"钩子兼容模式"并明确文档 |
| R5 | 硬件编码在工控机上不可用或质量差 | 高 | 中 | 主路径为纯 CPU 分块无损；硬件编码仅作加速，运行时探测 + 自动回退 |
| R6 | 文本/告警色保真不达标（4:2:0 污染） | 中 | 高 | 强制内容分类，文本块仅走无损/4:4:4；提供"像素完美模式"并在 CI 里做逐像素 diff 回归 |
| R7 | 弱网（1 Mbps/1% 丢包）体验崩塌 | 中 | 高 | 变化驱动 + 截止期丢弃 + FEC/NACK + 渐进精化；以 S7 为门禁指标 |
| R8 | 多观众时 CPU/带宽线性增长 | 中 | 中 | 一路编码多路分发；按最弱观众编码 + 差异化精化流 |
| R9 | 协议/编码在两端版本不一致导致花屏 | 中 | 高 | 严格版本协商 + 能力矩阵 + 全链路 CRC + "请求整帧"恢复机制 |
| R10 | GPL/AGPL 污染（参考了 VNC/Sunshine/RustDesk 代码） | 中 | 高 | **clean-room 实现**：只读论文/协议文档，不复制代码；建立第三方代码审计流程与 SBOM |
| R11 | 专利风险（渐进编码、分块压缩等老专利） | 低 | 中 | 做 FTO 检索（JPEG/JPEG2000/H.264 池已授权问题）；优先用已标准化、有明确许可的算法 |
| R12 | 等保/工控安全合规要求（审计、双因子、密码合规） | 高 | 中 | 国密算法可选（SM4-GCM）、审计日志、双因子；提前对齐 GB/T 22239 与工控防护要求 |
| R13 | 客户现场"禁装驱动/禁改系统" | 高 | 中 | 免驱模式为一等公民；便携版（单 exe 运行、无服务） |
| R14 | Win7 上 DPI/多屏/异形分辨率坐标错乱 | 中 | 中 | 统一走"物理像素 + 虚拟桌面坐标"；DPI 感知清单；自动化多屏回归测试 |
| R15 | 团队对采集/驱动/编解码的经验缺口 | 中 | 高 | 至少 1 名 Windows 内核/图形方向资深工程师；编解码可先用 FFmpeg 打底 |

### 6.3 三个"必须提前确认"的产品边界

1. **是否必须支持"被控端锁屏/登录界面可见"** —— 决定是否必须做驱动（成本差 3–5 人月 + 签名流程）。
2. **是否必须"多会话/多用户并行"** —— Win7 上不可能（无 IddCx），Win10+ 需自研虚拟显示驱动，且与 RDP 会话模型冲突。
3. **是否必须"仅查看（不被操作员察觉/不打断）"** —— 影响隐私屏与采集层设计（镜像驱动天然"旁路"，无感）。

## 7. 可行性验证计划（PoC，8 周）

**原则：先用 2 周证伪，再用 6 周证明。** 不要在没测过基线的情况下写第一行产品代码。

### 7.1 阶段 P0：基线测量（第 1–2 周）—— 决定"值不值得自研"

| 任务 | 方法 | 产出 |
|---|---|---|
| 搭建真实工控负载 | 在 Win7 与 Win10 各一台虚拟机/实机装 **WinCC / KingView(组态王) / InTouch** 之一，构造 5 个标准场景脚本：①静止 ②数值刷新 ③按钮/弹窗 ④报警列表 ⑤趋势曲线平移 + 画面切换 | 场景脚本 + 录制的"标准参考视频"（作为后续压缩比对比的黄金样本） |
| 采集基线数据 | 用 **TurboVNC/TigerVNC**（Tight/ZRLE，无损与有损各一档）、**RDP**（默认 + 4:4:4 若可用）、**Sunshine**（Win10 机器，5/10/20 Mbps）、**RustDesk**（平衡/低延迟）分别跑 5 场景 | 每个组合的：平均码率、峰值码率、帧率、端到端延迟、CPU、文本主观评分、ΔE |
| 网络条件矩阵 | 用 `tc netem` / 硬件限速器模拟：LAN(1G,0.3ms) / WiFi(30M,3ms,0.1%丢包) / 4G(2M,60ms,1%) / 极端(512k,150ms,3%) | 性能退化曲线表 |
| **门禁 G0** | 若"现有最优组合（VNC 无损 + RDP）"在场景①②已达到 S1–S3 目标，则**自研收益不足，应转为集成方案**（见第 11 章） | Go/No-Go 决策 |

> 预期结论（基于公开数据推断）：VNC 系在①②可达标但④⑤崩塌；RDP 在①②可达标但不可改造且 Win7 弱；**因此自研的收益集中在"③④⑤ + 多观众 + 无中心 + 审计"**，这正是产品价值所在。

### 7.2 阶段 P1：采集 + 编码内核原型（第 3–5 周）

- 实现 Win10 DDA 采集 + 64×64 分块 + xxHash 比对 + 三编码器（SOLID / PAL+RLE / JPEG444）；
- 实现 Win7 GDI 采集（免驱）+ 全帧比对（多线程 CRC）；
- 度量：单帧处理耗时、CPU 占用、5 场景码率与目标 S1–S4 的差距、逐像素 diff 通过率（S8）；
- **门禁 G1**：场景①②③ 码率 ≤ 目标值 1.5 倍，端到端（采集→本地回环解码）延迟 ≤ 40 ms，CPU ≤ 10%。

### 7.3 阶段 P2：传输 + 弱网（第 6–7 周）

- 实现 UDP 分片/FEC/NACK/拥塞控制 + 输入通道；用 netem 做 4 档网络；
- 度量：S5/S6/S7；丢包 3% 时的恢复时间与花屏残留；
- **门禁 G2**：1 Mbps/80 ms/1% 丢包下 ≥12 fps 且操作可感知无卡顿。

### 7.4 阶段 P3：Win7 驱动可行性（第 6–8 周，与 P2 并行）

- 基于开源 mirror driver 样本（如 DFMirage 风格的 `mirror` 示例）在 Win7 x64 上编译、自签、安装，验证：脏矩形正确性、帧率、CPU、蓝屏率（长时间跑 72h）、与杀软共存；
- **门禁 G3**：72 小时无蓝屏、脏区漏报率 <0.1%（用全帧比对交叉验证）、CPU <3%。

### 7.5 PoC 总门禁（G-Final）

| 判据 | 阈值 |
|---|---|
| 场景①②③ 码率 | 优于 RDP/VNC 基线 ≥ 40% |
| 场景④⑤ | 可用（≥10 fps）且码率 ≤ 4 Mbps |
| 端到端延迟 P95 | ≤ 150 ms（LAN） |
| 文本逐像素一致 | 100%（无损模式） |
| Win7 72h 稳定性 | 无崩溃/蓝屏 |
| 综合 | 若"优于基线 40%"不成立 → 放弃自研内核，转集成路线 |

## 10. 许可、合规与知识产权

| 事项 | 结论 |
|---|---|
| **nx-libs / x2go** | GPLv2。仅可"阅读思想"，不可复制代码进闭源产品；若要复用，唯一安全方式是**独立进程 + 明确协议边界**（仍有法律争议，不建议） |
| **RustDesk** | AGPLv3 —— 最严格的传染性（网络服务亦需开源）。**禁止任何代码复制**，仅可参考架构 |
| **Sunshine / Moonlight** | GPLv3（Sunshine）、GPLv3（Moonlight）。同上，不复制代码；FFmpeg 若使用需注意 LGPL/GPL 构建选项（用 LGPL 构建 + 动态链接） |
| **TigerVNC / TurboVNC** | GPLv2 / GPLv2。同上 |
| **FreeRDP** | Apache 2.0 —— **可以安全借鉴/复用**（RDP 客户端侧、部分编解码实现可参考甚至使用） |

## 11. Build / Buy / Hybrid 决策

### 11.1 三条路线

| 路线 | 内容 | 成本 | 低带宽性能 | 差异化 | 风险 |
|---|---|---|---|---|---|
| **A. 纯集成**（买/嵌 NoMachine 或自建 TigerVNC 方案 + 自研管理面） | 用现成引擎，只做工控外壳（审计、水印、地址簿、权限） | 低（60–100 万） | ★★☆ | ★★☆ | 受制于人、无法解决④⑤场景、无中心难实现 |
| **B. 混合**（VNC 协议族底座 + 自研分块/编码/传输插件） | 复用 RFB 的矩形模型与现成客户端生态，替换其编码与传输 | 中（150–200 万） | ★★★★ | ★★★★ | 受 RFB 模型限制（矩形无时间维） |
| **C. 全自研 NSU** | 本文第 5 章架构 | 高（300–350 万） | ★★★★★ | ★★★★★ | 工程与 Win7 驱动风险 |

### 11.2 决策建议

> **推荐 B → C 的渐进路径**：
> 1. **P0 用 2 周测基线**，确认现有方案在"曲线平移/画面切换/多观众/无中心"四点的具体缺口；
> 2. 若缺口主要是"④⑤ + 多观众"，先做 **B（混合）**：保留 RFB 兼容（可直接用 TigerVNC 客户端做对照与回退），但把"分块差分 + 内容分类 + UDP 传输 + 渐进精化"作为私有扩展（新 encoding），这样**6 个月内可交付 MVP，且始终有一个能用的回退路径**；
> 3. 当私有 extension 成为主路径、RFB 兼容性成为负担时（约 12–18 个月），再剥离为独立协议（C）。
>
> 这条路径的最大价值：**任何时刻都有可交付物，且每一步的投入都能被基线的实测数据证明是必要的。**

### 11.3 不适合继续投入的早期信号（Stop 判据）

- P0 实测显示 TigerVNC 无损 + 私有传输补丁已达 S1–S3，且④⑤通过"降低帧率 + 有损"可接受 → 转 A；
- Win7 mirror driver 在目标客户环境无法安装（签名/杀软/客户政策）且 GDI 回退性能不达标 → Win7 从"必须"降为"只读监视"，重构 Win7 策略；
- 团队 3 个月内做不出稳定的 DDA + 分块内核 → 团队能力/排期不匹配，转 B。

## 12. 结论

### 12.1 对"NX 协议"的判断

- **NX 协议本身不可行**：其核心优势源自 X11 语义代理（nxagent），Windows 没有对应层；NX 4+ 已闭源且转向"通用自适应显示协议"，x2go/nx-libs 停在 X11 且 GPL 传染。
- **NX 的思想高度可行且必要**：差分缓存、分块脏区、自适应编码、速率调度、会话保持 —— 这五项在 Windows 上全部可实现，且正是工控低带宽场景的胜负手。
- **NoMachine 的 Windows 版本身就是"NX 思想 + 驱动采集"的产物**，这反证了路线成立，同时说明本项目不可能靠"用 NX 协议"获得超出它的性能，只能靠**面向工控的内容感知编码 + 渐进精化 + 无中心**获得差异化。

### 12.2 最终结论

> **项目可行（综合 3.8/5），但必须重新定义技术命题**：
> 从"用 NX 协议做远程控制"改为"**用工控内容感知的分块差分协议（NSU）做超低带宽远程控制**"。
>
> 三个成败关键，按重要性排序：
> 1. **内容分类 + 无损文本路径 + 渐进精化**（决定低带宽下的画质与体验，是唯一真正的技术护城河）；
> 2. **变化驱动 + 截止期调度 + UDP/FEC**（决定弱网可用性）；
> 3. **Win7 驱动/工具链方案**（决定市场覆盖面，也是最大工期风险）。

### 12.3 建议立即执行的三件事（本周内）

1. **拉通场景定义**：确认第 6.3 节的三个产品边界（锁屏可见？多会话？无感监视？）—— 这三个答案会改变 30% 的架构工作量；
2. **搭 P0 基准平台**：一台 Win7 + 一台 Win10 + 组态王/WinCC 试用版 + `tc netem` 环境，2 周出基线数据；
3. **锁定两名关键人**：Windows 图形/驱动方向 + 实时传输方向，其余角色可后补。

| Build-to-Lossless | PCoIP 的渐进精化策略：先快速有损呈现，静止后逐轮精化至无损 |
| intra-refresh | 用帧内刷新条带替代 I 帧，避免码率尖峰与花屏持续 |
| FEC / NACK | 前向纠错 / 否定确认重传 |
| GCC / 延迟梯度 | Google 拥塞控制思路：以排队延迟梯度估计可用带宽 |
| SAS | Secure Attention Sequence（Ctrl+Alt+Del），需 `SendSAS` + 服务权限 |
